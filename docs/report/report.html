1. Requirements specification

1.1 Problem statement and goals

Students and teachers at SDU lose time on three everyday problems: finding a free classroom, reaching a teacher during office hours, and getting broken equipment fixed. Information about student initiatives and clubs is scattered over chats. SDU Bağdar puts these into one web application, signed in with an SDU e-mail address.

Goals

  • Show which rooms of the real SDU layout (blocks D to I) are free right now, filtered by building, floor, kind and capacity.
  • Let teachers publish office hours and let students book them manually or automatically, using a scheduling strategy chosen at request time.
  • Let any user report a facility problem, detect duplicate reports and let teachers drive them to resolution.
  • Let students discover initiatives, follow them, join clubs, answer club surveys and keep a profile with notification settings.
  • Keep the system maintainable: layered services, one database per service, three design patterns visible in working code.

2. Software design

2.3 How the three required design patterns are used

Strategy: office-hour scheduling (CampusPlus)

RequirementWhere it is met
Common strategy interfaceSchedulingStrategy with name() and choose(openSlots, request).
At least three concrete strategiesFirstAvailableStrategy ("first": earliest slot of the weekly order), EarliestDeadlineStrategy ("deadline": soonest slot that still happens before the student's deadline), PreferredTimeStrategy ("preferred": start time closest to the preferred time).
Select or switch at runtimeThe request POST /office-hours/book carries strategy. StrategyRegistry.get(name) resolves it per request; an unknown name returns 422 listing the valid names.
New strategy without rewriting the clientOfficeHourService only knows the interface and the registry. A new algorithm is one new class plus one register(...) call in CampusPlusMain. Unit test "a new strategy plugs in without changing existing code" registers a fourth strategy (last) and uses it while the other three keep working.

ProjectForge applies the same pattern for recommendations (popularity, recent, category); it is an extra, not needed for the assignment.

Adapter: SDU timetable import (CampusPlus)

RequirementWhere it is met
Component with an incompatible interfaceLegacyTimetableSystem simulates the university system. It exports pipe-separated text rows ROOM|WEEKDAY|HHMM_FROM|HHMM_TO|COURSE with numeric weekdays and HHMM integers.
Adapter makes it compatibleLegacyTimetableAdapter implements TimetableProvider. It parses the rows and returns typed FreeInterval objects between 08:30 and 18:00.
Original component not modifiedLegacyTimetableSystem has no dependency on the application and no change was needed to use it.
System uses it through the adapterRoomService depends on TimetableProvider only. GET /rooms returns freeUntil values computed from the legacy rows (verified by the end-to-end test free_rooms_come_through_the_timetable_adapter). Replacing the simulation by a real client means writing a new TimetableProvider.

Decorator: report processing (FixMyCampus)

RequirementWhere it is met
Common component interfaceReportProcessor.process(Report).
At least three concrete decoratorsValidationAuditDecorator (checks category and description length, audits REJECTED / SUBMITTED), DuplicateAlertDecorator (links duplicateOf, alerts the first reporter), NotificationDecorator (tells the reporter the report was received).
Each wraps another ReportProcessorEvery decorator holds a next field of the interface type and delegates to it. The innermost component is BaseReportProcessor, which only saves.
Combine multiple decoratorsReportPipelineFactory.build(names) stacks them in the order given by FIXMYCAMPUS_PIPELINE (default validation,duplicate,notification, outermost first). Any subset and any order works.
Add behaviour without modifying the originalBaseReportProcessor is never edited. The unit test "a new decorator wraps the chain without modifying it" adds a tracing decorator on top of the existing chain.

2.4 Important design decisions

DecisionReason
Microservices with one gatewayEach module (rooms, reports, initiatives) can change and fail independently; the frontend has a single address.
Database per service, no foreign keys across databasesNo hidden coupling. FixMyCampus asks CampusPlus over HTTP whether a room exists instead of reading its tables.
Identity from a signed token, not from the request bodyA client cannot grant itself the TEACHER role. Gateway and services both verify.
Device verification instead of passwords for studentsStudents sign in with an SDU e-mail. A 6-digit code registers the device once; the code is stored hashed, expires in 10 minutes and has a one-minute resend limit.
Ports and adapters (repository, sender, hasher interfaces)Business rules are testable without a database or mail server; the code sender can be mailer (SMTP) or console (development).
No application frameworksJDK HttpServer and Python http.server keep the dependency list to SQLite and logging jars, and make the layering explicit.
Validation at two levelsDecorators validate content; the service boundary still checks that the room exists, so rules hold even if the pipeline is configured without the validation decorator.
Simulated university dataTimetable, grades and the notification feed are deterministic demo data; the adapter and ports make replacing them a local change.

3.3 How data is stored and retrieved

  • Storage: one SQLite file per service in data/ (auth.db, campus.db, issues.db, social.db). Each service creates its schema and, when the database is empty, its demo data at start-up (CampusSchema, FixSchema, and the Python equivalents). The files are ignored by git, so every installation starts from clean seed data.
  • Access: only repository classes run SQL, with parameterised statements (user values are never concatenated into SQL). Java services use the Database helper: one connection per call, PRAGMA foreign_keys=ON, transactions for multi-row changes, and UNIQUE violations mapped to HTTP 409.
  • Retrieval: repositories return domain objects (Room, Report, ...). Services combine them with business rules; the presentation layer turns the result into JSON.
  • Integrity: CHECK constraints (roles, statuses, capacity, scores), UNIQUE keys (e-mail, club name, booking), foreign keys inside a database; cross-service references are validated over HTTP.
  • Secrets in data: passwords and verification codes are stored only as PBKDF2 hashes.

5.3 Sample data and initial preparation

  • Automatic: on first start each service creates its tables and fills them (campus layout, teacher offices and office hours, issue categories and sample reports, initiatives, clubs). Delete data/*.db and restart to reset everything.
  • Demo accounts (when CAMPUSOS_SEED_DEMO=true): student@sdu.edu.kz and teacher@sdu.edu.kz.
  • New student: no preparation; the account is created when the first verification code is requested for a valid @sdu.edu.kz address.
  • Teacher: use "Register as teacher" (invite code sdu-teacher unless disabled).

Known limitations

  • The university timetable, grades and the notification feed are simulated data (the Adapter and the ports isolate this).
  • The AI validation service is a local rule-based placeholder; an external provider can be set with AI_PROVIDER_URL.
  • Verification e-mail needs SMTP credentials; without them use the console delivery mode.
  • The Java auth code (AuthService) has no dedicated unit tests; it is covered by the end-to-end tests and manual checks.
